# 테스트 커버리지 측정 결과

측정 기준: 2026-09-05 UTC의 현재 작업 트리. 대상은 데스크톱 프런트엔드,
네이티브 Rust, 형제 저장소 `../mahoquot-proxy`의 Rust workspace다.
중첩된 `mahoquot-proxy` checkout은 대상이 아니다.

## 결론

테스트는 모두 통과했지만, 전체 코드의 충분한 검증이나 100% 완료를 뜻하지 않는다.
가장 큰 공백은 네이티브 앱 진입점과 macOS 통합, 프런트엔드 차트 렌더링이다.
프록시는 정상 경로에 비해 인증 갱신의 경합과 실패 복구 분기가 덜 실행됐다.
아래는 **테스트 코드를 제외한 계측 가능한 제품 코드** 기준이며,
줄은 실행 줄, 분기는 계측기가 내보낸 분기 결과, 함수는 계측 함수 기준이다.

이 표는 보강 전 기준선이다. 지목한 경로에 테스트를 추가한 뒤 다시 측정한 값은

미커버 위치는 결함 판정이 아니라 이 실행에서 검증되지 않은 경로다.

  기존 E2E 통과 수치를 이번 코드 커버리지에 합산하지 않았다.
- 초기 V8 보고서에는 미실행 파일에 synthetic empty-report 함수 37개가 생겼고,

- 프런트엔드 statement 커버리지는 58.17% (2,609/4,485)다.

### Rust

- `cargo-llvm-cov 0.9.0`, `rustc 1.99.0-nightly (daf2e5e18 2026-07-13)`,
  LLVM 22.1.8, `aarch64-apple-darwin`, debug/default-feature 빌드.
- `--branch --no-cfg-coverage --no-cfg-coverage-nightly`를 사용했다.
  계측 전용 cfg로 제품 코드가 달라지지 않도록 했으며,
  네이티브의 `isolated-secret-tests` 기능은 켜지 않았다.
- 두 저장소 각각 `target/coverage-20260905`에 계측 산출물을 격리했다.
  테스트 포트 충돌을 피하려고 프록시 테스트 이후 네이티브 테스트를 실행했다.
- cargo-llvm-cov가 별도 테스트 파일을 기본 제외하더라도 인라인 `#[cfg(test)]`
  코드까지 자동으로 빼지는 않는다. ast-grep의 Rust AST로 실제 item 범위를 찾고,
  macOS/default/debug cfg에서 제품에 포함되지 않는 테스트 전용 item을 제거했다.
  단순히 `mod tests` 이후 전부를 자르는 방식은 쓰지 않았다.
- `any(test, feature = "isolated-secret-tests")`는 현재 feature 조건에 따라 제외하고,
  `any(test, target_os = "macos")`처럼 실제 제품에도 들어가는 item은 유지했다.
  제외 범위와 파일별 SHA-256은 `*-filtered.manifest.json`에 있다.
- 프록시 제품 코드에서 테스트 전용 DA 5,998줄, 함수 595개, BRDA 결과 78개를 제거했다.
  네이티브에서는 1,516줄, 함수 119개, BRDA 결과 20개를 제거했다.
- 프록시의 도구·벤치·catalog CLI 6개 계측 파일은 제품 합계와 분리했다.
  이들의 줄 커버리지는 44.60% (351/787), 분기 26.67% (40/150), 함수 31.87% (29/91)다.
  실행되지 않은 example `crates/gateway/examples/settings_read_cost.rs`도 목록에 별도 기록했다.

**Rust 수치 해석에 필요한 한계:**

1. 줄은 LCOV `DA`, 분기는 `BRDA`의 실제 레코드를 재집계했다.
   이 도구 버전의 원본 `LF/LH/BRH` 요약과 실제 레코드 수가 다른 파일이 있으므로
   원본 요약을 그대로 뺄셈하지 않았다. 모든 차이는 `summary_discrepancies`에 보존했다.
   함수는 동일 소스 위치의 제네릭 인스턴스를 LLVM JSON으로 묶어 원본 FNF/FNH와 대조했다.
2. **분기 수치는 모든 Rust 제어 흐름의 비율이 아니다.** 매크로·일부 match/오류 경로에
   DA는 있지만 BRDA가 없는 사례가 있다. 네이티브 `main.rs`는 줄 8.72%인데도
   분기 100% (10/10)로 나온다. 계측된 분기 10개가 통과했다는 뜻이지 main의 모든
   조건문이 검증됐다는 뜻이 아니다. MC/DC는 수집하지 않았다.
3. 프록시 제품 소스 76파일 중 72개에 카운터가 있다. 나머지는
   `compat/cursor_proto.rs`, `lib.rs`, `registry/error.rs`, `registry/mod.rs`로,
   선언·derive·모듈 재수출 파일이다. 미계측 소스를 100%로 간주하지 않았다.
   네이티브 제품 소스 14파일 중 `platform/mod.rs`를 제외한 13개에 카운터가 있다.
4. 네이티브 `platform/windows.rs`, `platform/linux.rs`는 macOS cfg에서 빌드되지 않아
   분모에 없다. 다른 OS, release 전용 조건, feature 조합, doctest는 이 측정으로 보장하지 않는다.

참고로 테스트 코드가 섞인 원본 LLVM 요약의 줄 수치는 프록시 83.38%
(24,407/29,273), 네이티브 61.23% (3,351/5,473)였다.
이는 분모와 줄 집계 방식이 다른 원본 진단값이며 최종 제품 커버리지로 쓰지 않는다.

## 우선 확인할 미커버 경로

### 프록시: 인증·키 갱신·스트림·오류 복구

아래 경로는 모두 `../mahoquot-proxy` 기준이다. 소스, 제품 전용 LCOV와
파일 hash를 대조했다. 정상 키 회전과 스트림 종료 테스트가 없다는 뜻이 아니라,
그 테스트들이 아래 대체·실패 경로까지 실행하지 않았다는 뜻이다.

1. **마스터 키 없이 scoped key로 인증:** `crates/gateway/src/inbound.rs:126-138`,
   `ApiKeys::authorizes`. credential을 제시한 분기 hit 0, 제시하지 않은 분기 130.
   128-135, 137-138의 10개 실행 줄이 미커버다.
   마스터 키가 없는 설정에서 유효 scoped key를 실제 middleware로 전달해
   Scoped identity와 relay 제한, management 403을 검증할 가치가 있다.
   → 닫힘. `review_auth_recovery.rs`의 3개 테스트가 이 분기를 실행한다.
2. **동시 token 갱신의 중복 방지:** `crates/gateway/src/account.rs:1060-1069`,
   `AccountMember::refresh`. lock 획득 후 이미 바뀐 token을 감지하는
   1068의 조기 반환 분기 hit 0, 갱신 필요 분기 7; 1069는 미실행이다.
   같은 stale token을 제시하는 두 호출을 이벤트로 동기화하고,
   token 교환 1회와 두 번째 반환값 false, 메모리·저장 token 일치를 확인해야 한다.
   → 닫힘. stale token 재제시가 두 번째 refresh를 소비하지 않음을 확인한다.
3. **scoped key 회전의 경계 조건:** `crates/gateway/src/management/scoped_keys.rs:187-200`.
   정상 교체는 실행됐다. 하지만 188의 tracker 없음 결과는 0/6,
   196의 공백-only replacement 결과는 0/2다.
   tracker entry가 없는 키의 회전과 공백-only patch에서 기존 key identifier,
   사용량·권한 제한이 보존되는지를 분리해 검증할 수 있다.
   → 196의 공백-only 분기는 닫혔다. 188의 tracker 없음 분기는 결정적으로
   재현할 수 없어 남겼고, 이유는 아래 "의도적으로 테스트하지 않은 경로"에 있다.
4. **stream 시작 후 전송 오류:** `crates/gateway/src/compat/mod.rs:372-377`의
   `Some(Err(err))` 6줄과 `error_frames`의 440-447 전부 0 hit다.
   첫 유효 이벤트 전달 뒤 upstream body를 명시적으로 중단하고 OpenAI/Anthropic
   오류 프레임, 정상 완료로 오인하지 않는 종료, 종료 후 추가 프레임 부재를 확인해야 한다.
   이 match 오류 arm은 줄 카운터가 있지만 직접 대응하는 BRDA는 없다.
   → 372-377은 닫혔다. 440-441도 실행되며 442만 도달 불가능해 남았다.
5. **갱신 실패 후 failover:** `crates/gateway/src/relay.rs:1644-1661`의
   proactive-refresh 실패 18줄과 1737-1745의 refresh-and-replay 전송 실패 9줄이 0 hit다.
   두 계정 fixture에서 인증 거절, token endpoint 네트워크 실패, replay 네트워크 실패를
   각각 주입해 다음 계정 선택, 실패 계수와 monitor 기록, 인증 거절만 AuthFailed가
   되는지 검증할 가치가 있다.
   → 닫힘. `review_relay_recovery.rs`의 3개 테스트가 두 경로를 모두 실행한다.
6. **terminal 401과 일반 403의 구분:** `crates/gateway/src/relay.rs:1939-1963`.
   두 상태 처리 블록의 22개 실행 줄이 0 hit이고 1939/1952 BRDA 결과 모두 `-`다.
   model rejection이 아닌 403과 갱신 성공 후 재발한 401을 따로 만들어,
   failover 및 health/추가 갱신 여부를 확인해야 한다.
   → 닫힘. 403은 quarantine 없이 failover하고 401은 AuthFailed가 됨을 확인한다.

Bun 1.4.0, Node 22.22.3, Python 3.12, ast-grep 0.44.1 및 위 Rust 도구 체인 기준이다.
같은 수치를 기대하려면 같은 소스 snapshot과 도구 버전을 사용해야 한다.

프런트엔드:

```bash
bun --cwd crates/monitor-ui/frontend install --frozen-lockfile
bun --cwd crates/monitor-ui/frontend run typecheck
bun --cwd crates/monitor-ui/frontend run test:coverage
```

Rust는 두 저장소 테스트를 순차 실행한다. 아래는 이번과 같은 계측 옵션을 사용하되
기존 결과와 섞이지 않는 새 target/evidence 경로를 만드는 재현 명령이다.
네이티브 계측 빌드에서 gateway 재빌드는 생략하지만 네이티브 테스트는 실행한다.

```bash
set -euo pipefail
DESKTOP="$PWD"
PROXY="$(cd ../mahoquot-proxy && pwd)"
RUN="$(date -u +%Y%m%dT%H%M%SZ)-$$"
OUT="$DESKTOP/.omo/evidence/coverage-$RUN"
FILTER="$DESKTOP/.omo/evidence/coverage-2026-09-05/rust-coverage-filter/rust_coverage_filter.py"
mkdir -p "$OUT"

(cd "$(dirname "$FILTER")" && python3 -m unittest -v test_filter)

for name in proxy native; do
  (
    if [ "$name" = proxy ]; then
      cd "$PROXY"
    else
      cd "$DESKTOP"
      export MAHOQUOT_SKIP_GATEWAY_BUILD=1
    fi
    export CARGO_BUILD_JOBS=4
    export CARGO_LLVM_COV_TARGET_DIR="$PWD/target/coverage-$RUN"
    cargo +nightly llvm-cov --workspace --no-fail-fast --branch \
      --no-cfg-coverage --no-cfg-coverage-nightly --no-report \
      2>&1 | tee "$OUT/$name-test.log"
    cargo +nightly llvm-cov report --json --output-path "$OUT/$name.json"
    cargo +nightly llvm-cov report --lcov --output-path "$OUT/$name.lcov"
    python3 "$FILTER" filter --repo "$PWD" \
      --lcov "$OUT/$name.lcov" --llvm-json "$OUT/$name.json" \
      --out-prefix "$OUT/$name-filtered"
  )
done
```

이번 재측정은 동일한 로직에 `RUN=20260905-recheck`만 바꿔 실행했다. 단, rustc가
임시 파일을 쓰는 부팅 볼륨이 가득 차 먼저 실패했으므로 `TMPDIR`을 여유 있는
볼륨으로 지정해야 한다(예: `export TMPDIR=/Volumes/T9-Mac/tmp`). 이는 측정 결과가
아니라 재현 환경 조건이다.

후처리 도구는 이번 macOS/default/debug 소스 구조를 위한 로컬 도구다.
다른 target/feature로 바꾸면 이 manifest를 재사용하지 말고 해당 계측 조건으로
분모 산정도 다시 해야 한다. 지원하지 않는 cfg나 해석되지 않는 소스 구조는
오류로 중단하며 임의로 제품 분모에서 제거하지 않는다.
